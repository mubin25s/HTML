What Are Design Patterns?

Reusable solutions to commonly occurring problems in software design. They're blueprints, not code — a language shared by developers.

Structural

🏗️ Structural Patterns

Deal with how classes and objects are composed to form larger structures.

Patterns: Facade, Adapter, Decorator
Behavioural

⚙️ Behavioural Patterns

Deal with communication and responsibility between objects.

Patterns: Observer, Chain of Responsibility
Creational

🏭 Creational Patterns

Deal with object creation mechanisms to increase flexibility.

Patterns: Singleton, Factory, Builder
💡

// Structural Pattern 01

Facade Pattern

The Facade pattern provides a simplified interface to a complex subsystem. Instead of the client interacting with multiple classes, it talks to one "front door" — the Facade.

🎯

Real-life analogy: A hotel concierge. You say "I need a taxi, dinner reservation, and dry cleaning." The concierge coordinates all the subsystems for you. You don't deal with each department yourself.

UML Diagram

Step-by-Step Explanation

  1. Create the Subsystem classes — each handles one specific job.
  2. Create the Facade class — it holds references to all subsystems.
  3. The Facade exposes one simple method (e.g. startExam()) that internally calls all subsystems.
  4. The Client only talks to the Facade — never to the subsystems directly.

Java Implementation

JAVA · Facade Pattern 
// ── SUBSYSTEMS ──────────────────────────────────────────

class AuthenticationService {
    public void verifyCredentials(String studentId) {
        System.out.println("✓ Auth: Student " + studentId + " verified.");
    }
}

class QuestionService {
    public void loadQuestions(String courseId) {
        System.out.println("✓ Questions loaded for course: " + courseId);
    }
}

class TimerService {
    public void startTimer(int minutes) {
        System.out.println("✓ Timer started: " + minutes + " minutes.");
    }
}

// ── FACADE ──────────────────────────────────────────────

class ExamFacade {
    private AuthenticationService auth   = new AuthenticationService();
    private QuestionService       qSvc   = new QuestionService();
    private TimerService          timer  = new TimerService();

    // ONE simple method the client calls
    public void startExam(String studentId, String courseId, int duration) {
        System.out.println("\n=== Starting Exam Session ===");
        auth.verifyCredentials(studentId);
        qSvc.loadQuestions(courseId);
        timer.startTimer(duration);
        System.out.println("=== Exam Ready! Good luck! ===");
    }
}

// ── CLIENT (Main) ────────────────────────────────────────

public class Main {
    public static void main(String[] args) {
        ExamFacade exam = new ExamFacade();
        // Client calls ONE method — all complexity is hidden
        exam.startExam("STU001", "CS311", 90);
    }
}

/* OUTPUT:
=== Starting Exam Session ===
✓ Auth: Student STU001 verified.
✓ Questions loaded for course: CS311
✓ Timer started: 90 minutes.
=== Exam Ready! Good luck! ===
*/
// Structural Pattern 02

Adapter Pattern

The Adapter pattern acts as a bridge between two incompatible interfaces. It wraps an existing class so it can be used where a different interface is expected — without changing source code.

🔌

Real-life analogy: A power socket adapter. Your laptop charger has a 3-pin plug, but the wall has a 2-pin socket. The adapter makes them compatible — neither the charger nor the wall changes.

UML Diagram

Java Implementation

JAVA · Adapter Pattern 
// ── TARGET INTERFACE (what the system expects) ───────────

interface BookFile {
    void open();
}

// ── CONCRETE COMPONENT: native PDF (already compatible) ──

class PDFBookFile implements BookFile {
    private String fileName;

    PDFBookFile(String fileName) { this.fileName = fileName; }

    public void open() {
        System.out.println("📄 Opening PDF: " + fileName);
    }
}

// ── ADAPTEE: EbookFile has a DIFFERENT interface ─────────

class EbookFile {
    private String title;

    EbookFile(String title) { this.title = title; }

    // Different method name — incompatible with BookFile!
    public void readEbook() {
        System.out.println("📱 Reading Ebook: " + title);
    }
}

// ── ADAPTER: makes EbookFile compatible with BookFile ────

class EbookAdapter implements BookFile {
    private EbookFile ebook;   // wraps the adaptee

    EbookAdapter(EbookFile ebook) { this.ebook = ebook; }

    public void open() {          // translates open() → readEbook()
        ebook.readEbook();
    }
}

// ── MAIN ─────────────────────────────────────────────────

public class Main {
    public static void main(String[] args) {
        // Both treated uniformly via BookFile interface
        BookFile pdf   = new PDFBookFile("ResearchPaper.pdf");
        BookFile ebook = new EbookAdapter(new EbookFile("CleanCode"));

        pdf.open();    // 📄 Opening PDF: ResearchPaper.pdf
        ebook.open(); // 📱 Reading Ebook: CleanCode
    }
}
// Structural Pattern 03

Decorator Pattern

The Decorator pattern attaches new behaviours to objects dynamically by wrapping them in decorator objects. It's an alternative to subclassing for extending functionality.

☕

Real-life analogy: Ordering coffee. You start with a plain coffee, then add milk (+cost), then add sugar (+cost). Each addition "decorates" the original without creating a new class for every combo.

UML Diagram

Java Implementation

JAVA · Decorator Pattern 
// ── COMPONENT INTERFACE ──────────────────────────────────

interface Coffee {
    String getDescription();
    double getCost();
}

// ── CONCRETE COMPONENT ───────────────────────────────────

class PlainCoffee implements Coffee {
    public String getDescription() { return "Plain Coffee"; }
    public double getCost()        { return 1.00; }
}

// ── ABSTRACT DECORATOR ───────────────────────────────────

abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee;   // wraps a Coffee

    CoffeeDecorator(Coffee c) { this.decoratedCoffee = c; }

    public String getDescription() { return decoratedCoffee.getDescription(); }
    public double getCost()        { return decoratedCoffee.getCost(); }
}

// ── CONCRETE DECORATORS ──────────────────────────────────

class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee c) { super(c); }

    public String getDescription() {
        return decoratedCoffee.getDescription() + ", Milk";
    }
    public double getCost() {
        return decoratedCoffee.getCost() + 0.50;
    }
}

class SugarDecorator extends CoffeeDecorator {
    SugarDecorator(Coffee c) { super(c); }

    public String getDescription() {
        return decoratedCoffee.getDescription() + ", Sugar";
    }
    public double getCost() {
        return decoratedCoffee.getCost() + 0.25;
    }
}

// ── MAIN ─────────────────────────────────────────────────

public class Main {
    public static void main(String[] args) {
        Coffee coffee = new PlainCoffee();
        System.out.println(coffee.getDescription() + " → $" + coffee.getCost());

        coffee = new MilkDecorator(coffee);
        System.out.println(coffee.getDescription() + " → $" + coffee.getCost());

        coffee = new SugarDecorator(coffee);
        System.out.println(coffee.getDescription() + " → $" + coffee.getCost());
    }
}

/* OUTPUT:
Plain Coffee → $1.0
Plain Coffee, Milk → $1.5
Plain Coffee, Milk, Sugar → $1.75
*/
// Behavioural Pattern 01

Observer Pattern

The Observer pattern defines a one-to-many dependency. When one object (Subject) changes state, all its dependents (Observers) are automatically notified.

📢

Real-life analogy: YouTube subscriptions. When a channel (Subject) uploads a video, all subscribers (Observers) get notified. Subscribers can subscribe or unsubscribe anytime.

UML Diagram

Java Implementation

JAVA · Observer Pattern 
import java.util.*;

// ── OBSERVER INTERFACE ───────────────────────────────────

interface Observer {
    void update(String message);
}

// ── SUBJECT INTERFACE ────────────────────────────────────

interface Subject {
    void subscribe(Observer o);
    void unsubscribe(Observer o);
    void notifyObservers();
}

// ── CONCRETE SUBJECT ─────────────────────────────────────

class ClassroomNotifier implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private String message;

    public void subscribe(Observer o)   { observers.add(o); }
    public void unsubscribe(Observer o) { observers.remove(o); }

    public void notifyObservers() {
        for (Observer o : observers) o.update(message);
    }

    public void publishNotification(String msg) {
        this.message = msg;
        System.out.println("\n📣 Notification: " + msg);
        notifyObservers();
    }
}

// ── CONCRETE OBSERVERS ───────────────────────────────────

class Student implements Observer {
    private String name;
    Student(String name) { this.name = name; }

    public void update(String message) {
        System.out.println("  [Student] " + name + " received: " + message);
    }
}

class Teacher implements Observer {
    private String name;
    Teacher(String name) { this.name = name; }

    public void update(String message) {
        System.out.println("  [Teacher] " + name + " received: " + message);
    }
}

// ── MAIN ─────────────────────────────────────────────────

public class Main {
    public static void main(String[] args) {
        ClassroomNotifier notifier = new ClassroomNotifier();

        Student s1 = new Student("Alice");
        Student s2 = new Student("Bob");
        Teacher t1 = new Teacher("Dr. Smith");

        notifier.subscribe(s1);
        notifier.subscribe(s2);
        notifier.subscribe(t1);

        notifier.publishNotification("Class Routine Published");

        notifier.unsubscribe(s2);   // Bob unsubscribes
        notifier.publishNotification("Exam Routine Published");
    }
}

/* OUTPUT:
📣 Notification: Class Routine Published
  [Student] Alice received: Class Routine Published
  [Student] Bob received: Class Routine Published
  [Teacher] Dr. Smith received: Class Routine Published

📣 Notification: Exam Routine Published
  [Student] Alice received: Exam Routine Published
  [Teacher] Dr. Smith received: Exam Routine Published
*/
// Behavioural Pattern 02

Chain of Responsibility

The Chain of Responsibility pattern passes a request along a chain of handlers. Each handler decides either to process the request or pass it to the next handler.

🎫

Real-life analogy: Customer service escalation. You call Level 1 support. If they can't help, they forward to Level 2, then Level 3. Each level tries to handle it before escalating.

UML Diagram (Task 4)

Java Implementation

JAVA · Chain of Responsibility 
// ── ABSTRACT HANDLER ─────────────────────────────────────

abstract class SupportHandler {
    protected SupportHandler nextHandler;

    public SupportHandler setNext(SupportHandler next) {
        this.nextHandler = next;
        return next;   // enables chaining: h1.setNext(h2).setNext(h3)
    }

    public abstract void handleRequest(int level, String issue);
}

// ── CONCRETE HANDLERS ────────────────────────────────────

class Level1Support extends SupportHandler {
    public void handleRequest(int level, String issue) {
        if (level == 1) {
            System.out.println("✅ Level 1 resolved: " + issue);
        } else if (nextHandler != null) {
            System.out.println("⬆️  Level 1 forwarding to Level 2...");
            nextHandler.handleRequest(level, issue);
        }
    }
}

class Level2Support extends SupportHandler {
    public void handleRequest(int level, String issue) {
        if (level == 2) {
            System.out.println("✅ Level 2 resolved: " + issue);
        } else if (nextHandler != null) {
            System.out.println("⬆️  Level 2 forwarding to Level 3...");
            nextHandler.handleRequest(level, issue);
        }
    }
}

class Level3Support extends SupportHandler {
    public void handleRequest(int level, String issue) {
        System.out.println("🔴 Level 3 (Critical) resolved: " + issue);
    }
}

// ── MAIN ─────────────────────────────────────────────────

public class Main {
    public static void main(String[] args) {
        SupportHandler l1 = new Level1Support();
        SupportHandler l2 = new Level2Support();
        SupportHandler l3 = new Level3Support();

        l1.setNext(l2).setNext(l3);  // build the chain

        System.out.println("--- Issue 1 (Basic) ---");
        l1.handleRequest(1, "Password reset");

        System.out.println("\n--- Issue 2 (Intermediate) ---");
        l1.handleRequest(2, "Software crash");

        System.out.println("\n--- Issue 3 (Critical) ---");
        l1.handleRequest(3, "Data breach");
    }
}

/* OUTPUT:
--- Issue 1 (Basic) ---
✅ Level 1 resolved: Password reset

--- Issue 2 (Intermediate) ---
⬆️  Level 1 forwarding to Level 2...
✅ Level 2 resolved: Software crash

--- Issue 3 (Critical) ---
⬆️  Level 1 forwarding to Level 2...
⬆️  Level 2 forwarding to Level 3...
🔴 Level 3 (Critical) resolved: Data breach
*/
// Design Principles

SOLID Principles

SOLID is a set of five principles that make software designs more understandable, flexible, and maintainable. They're the foundation behind why design patterns work.

S

Single Responsibility

A class should have only one reason to change. One class = one job.

✓ UserAuth handles auth only — not email sending
O

Open/Closed

Classes should be open for extension but closed for modification.

✓ Add a new decorator without changing existing classes
L

Liskov Substitution

Subclasses should be substitutable for their parent class without breaking the program.

✓ Any Observer implementation should work where Observer is expected
I

Interface Segregation

Clients should not be forced to depend on interfaces they don't use. Keep interfaces small and specific.

✓ Separate Readable and Writable instead of one huge interface
D

Dependency Inversion

High-level modules should not depend on low-level modules. Both should depend on abstractions (interfaces).

✓ Facade depends on interfaces, not concrete services
🔗

SOLID + Patterns: Observer follows SRP (each observer has one job) and OCP (add observers without changing Subject). Chain of Responsibility follows OCP (add new levels without changing existing). Decorator follows OCP perfectly — you extend behavior by wrapping, not modifying.

// ── COMPONENT INTERFACE ──────────────────────────────────

interface Coffee {
    String getDescription();
    double getCost();
}

// ── CONCRETE COMPONENT ───────────────────────────────────

class PlainCoffee implements Coffee {
    public String getDescription() {
        return "Plain Coffee";
    }
    public double getCost() {
        return 1.00;
    }
}

// ── DECORATOR INTERFACE / ABSTRACT CLASS ─────────────────

abstract class CoffeeDecorator implements Coffee {
    protected Coffee decoratedCoffee;

    public CoffeeDecorator(Coffee coffee) {
        this.decoratedCoffee = coffee;
    }

    public String getDescription() {
        return decoratedCoffee.getDescription();
    }

    public double getCost() {
        return decoratedCoffee.getCost();
    }
}

// ── CONCRETE DECORATORS ──────────────────────────────────

class MilkDecorator extends CoffeeDecorator {

    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    public String getDescription() {
        return decoratedCoffee.getDescription() + ", Milk";
    }

    public double getCost() {
        return decoratedCoffee.getCost() + 0.50;
    }
}

class SugarDecorator extends CoffeeDecorator {

    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    public String getDescription() {
        return decoratedCoffee.getDescription() + ", Sugar";
    }

    public double getCost() {
        return decoratedCoffee.getCost() + 0.25;
    }
}

// ── MAIN ─────────────────────────────────────────────────

public class Main {
    public static void main(String[] args) {

        // Order 1: Plain coffee only
        Coffee order1 = new PlainCoffee();
        System.out.println("Order 1: " + order1.getDescription()
                           + " → $" + order1.getCost());

        // Order 2: Coffee + Milk
        Coffee order2 = new MilkDecorator(new PlainCoffee());
        System.out.println("Order 2: " + order2.getDescription()
                           + " → $" + order2.getCost());

        // Order 3: Coffee + Milk + Sugar (layered decorating)
        Coffee order3 = new SugarDecorator(
                            new MilkDecorator(
                                new PlainCoffee()));
        System.out.println("Order 3: " + order3.getDescription()
                           + " → $" + order3.getCost());

        // Order 4: Double Sugar!
        Coffee order4 = new SugarDecorator(
                            new SugarDecorator(
                                new PlainCoffee()));
        System.out.println("Order 4: " + order4.getDescription()
                           + " → $" + order4.getCost());
    }
}

/* OUTPUT:
Order 1: Plain Coffee → $1.0
Order 2: Plain Coffee, Milk → $1.5
Order 3: Plain Coffee, Milk, Sugar → $1.75
Order 4: Plain Coffee, Sugar, Sugar → $1.5
*/
