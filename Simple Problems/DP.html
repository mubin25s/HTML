Factory Pattern

Create objects without exposing instantiation logic to the caller

Intent
Delegate object creation to a factory method
When to Use
When the exact type isn't known until runtime
Benefit
Caller doesn't need to know new Dog() or new Cat()
AnimalFactory.java 
// ── Product interface ────────────────────────────────────
interface Animal {
    void speak();
}

// ── Concrete products ─────────────────────────────────────
class Dog implements Animal {
    public void speak() {
        System.out.println("Woof! 🐶");
    }
}

class Cat implements Animal {
    public void speak() {
        System.out.println("Meow! 🐱");
    }
}

// ── Factory ───────────────────────────────────────────────
class AnimalFactory {
    public static Animal create(String type) {
        return switch (type.toLowerCase()) {
            case "dog"  -> new Dog();
            case "cat"  -> new Cat();
            default       -> throw new IllegalArgumentException(
                                    "Unknown animal: " + type);
        };
    }
}

// ── Usage ─────────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        Animal a = AnimalFactory.create("dog");
        a.speak();    // Woof! 🐶

        Animal b = AnimalFactory.create("cat");
        b.speak();    // Meow! 🐱
    }
}
▶ Output
$ java Main
Woof! 🐶
Meow! 🐱
💡 Key Insight: The caller only knows about the Animal interface. Adding a new Bird class only requires updating the factory — not the calling code. This is the Open/Closed Principle in action.

Singleton Pattern

Ensure only one instance of a class exists — globally accessible

Intent
One and only one instance, ever
Use Cases
DB connection, Config manager, Logger
Thread Safety
Double-checked locking + volatile
DatabaseConnection.java 
public class DatabaseConnection {

    // 1. Volatile ensures visibility across threads
    private static volatile DatabaseConnection instance;
    private String url;

    // 2. Private constructor — prevents `new DatabaseConnection()`
    private DatabaseConnection() {
        url = "jdbc:mysql://localhost:3306/mydb";
        System.out.println("✅ DB Connection created.");
    }

    // 3. Thread-safe access (double-checked locking)
    public static DatabaseConnection getInstance() {
        if (instance == null) {
            synchronized (DatabaseConnection.class) {
                if (instance == null) {
                    instance = new DatabaseConnection();
                }
            }
        }
        return instance;
    }

    public void query(String sql) {
        System.out.printf("🗄️  [%s]  %s%n", url, sql);
    }
}

// ── Usage ─────────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        DatabaseConnection db1 = DatabaseConnection.getInstance();
        DatabaseConnection db2 = DatabaseConnection.getInstance();

        db1.query("SELECT * FROM users");

        // Proves same instance:
        System.out.println(db1 == db2);   // true ✅
    }
}
▶ Output
$ java Main
✅ DB Connection created.
🗄️ [jdbc:mysql://localhost:3306/mydb] SELECT * FROM users
true
⚠️ Why volatile? Without volatile, another thread might see a partially constructed object due to CPU instruction reordering. volatile forces a full memory barrier and ensures the object is fully visible before use.

Prototype Pattern

Clone an existing object instead of creating from scratch

Intent
Copy a configured object and customize it
When to Use
Object creation is expensive or complex
Watch Out
Deep copy vs shallow copy — collections need care
UserProfile.java 
// ── Prototype interface ───────────────────────────────────
interface Prototype {
    Prototype clone();
}

// ── Concrete prototype ────────────────────────────────────
class UserProfile implements Prototype {
    private String       name;
    private String       role;
    private List<String> permissions;

    public UserProfile(String name, String role,
                       List<String> permissions) {
        this.name        = name;
        this.role        = role;
        // Deep copy — so clones get independent lists
        this.permissions = new ArrayList<>(permissions);
    }

    @Override
    public UserProfile clone() {
        return new UserProfile(this.name,
                                this.role,
                                this.permissions);
    }

    public void setName(String name) { this.name = name; }

    @Override
    public String toString() {
        return "UserProfile{name='" + name
             + "', role='" + role
             + "', perms=" + permissions + "}";
    }
}

// ── Usage ─────────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        UserProfile template = new UserProfile(
            "Template", "ADMIN",
            List.of("READ", "WRITE", "DELETE"));

        // Clone and customize — no expensive re-setup
        UserProfile alice = template.clone();
        alice.setName("Alice");

        UserProfile bob = template.clone();
        bob.setName("Bob");

        System.out.println(alice);
        System.out.println(bob);
    }
}
▶ Output
$ java Main
UserProfile{name='Alice', role='ADMIN', perms=[READ, WRITE, DELETE]}
UserProfile{name='Bob', role='ADMIN', perms=[READ, WRITE, DELETE]}
💡 Deep vs Shallow Copy: Always use new ArrayList<>(original) when cloning lists. A shallow copy would share the same list reference — modifying alice.permissions would also modify bob.permissions!

Code Smell & Refactoring

Identify bad patterns and transform them into clean, maintainable code

Smell #1
Magic numbers (1, 2, 3.14159)
Smell #2
Meaningless names (p, x, t, O)
Smell #3
God method — does everything
❌ Before — Smelly Code
// SMELLS FOUND:
// - Meaningless class & method names
// - Magic numbers (1, 2, 3)
// - Hardcoded PI (use Math.PI!)
// - One method doing everything
// - Hard to extend with new shapes

public class O {   // 😱 what is O?
    public void p(int x,
                   int y,
                   int t) {
        if (t == 1) {   // what is 1?
            double r = x * 3.14159 * 3.14159;
            System.out.println("Area: " + r);
        } else if (t == 2) {
            double r = x * y;
            System.out.println("Area: " + r);
        } else if (t == 3) {
            double r = 0.5 * x * y;
            System.out.println("Area: " + r);
        }
    }
}
✅ After — Clean Code
// FIXED:
// + Interface for extensibility (OCP)
// + Descriptive names
// + Each class owns one responsibility
// + No magic numbers
// + Easy to add new shapes

interface Shape {
    double calculateArea();
}

class Circle implements Shape {
    private static final double PI = Math.PI;
    private final double radius;
    public Circle(double r) { radius = r; }
    @Override
    public double calculateArea() {
        return PI * radius * radius;
    }
}

class Rectangle implements Shape {
    private final double width, height;
    public Rectangle(double w, double h) {
        width=w; height=h;
    }
    @Override
    public double calculateArea() {
        return width * height;
    }
}

class Triangle implements Shape {
    private final double base, height;
    public Triangle(double b, double h) {
        base=b; height=h;
    }
    @Override
    public double calculateArea() {
        return 0.5 * base * height;
    }
}
Main.java — Clean usage 
public class Main {
    public static void main(String[] args) {
        List<Shape> shapes = List.of(
            new Circle(5),
            new Rectangle(4, 6),
            new Triangle(3, 8)
        );

        shapes.forEach(s ->
            System.out.printf("%s area: %.2f%n",
                s.getClass().getSimpleName(),
                s.calculateArea())
        );
    }
}
▶ Output
$ java Main
Circle area: 78.54
Rectangle area: 24.00
Triangle area: 12.00
🔑 SOLID Principles Applied: The refactored code follows Single Responsibility (each class manages one shape) and Open/Closed (add new shapes by creating new classes, never editing existing ones).

Exception Handling

Be specific, descriptive, and never swallow errors silently

Rule #1
Use specific exceptions, not generic Exception
Rule #2
Custom domain exceptions carry context data
Rule #3
Never: catch(e) {} — that's a silent failure bug
BankAccount.java 
// ── Custom exception carries context ─────────────────────
class InsufficientFundsException extends Exception {
    private final double shortfall;

    public InsufficientFundsException(double shortfall) {
        super(String.format("Insufficient funds. Short by: $%.2f",
                             shortfall));
        this.shortfall = shortfall;
    }

    public double getShortfall() { return shortfall; }
}

// ── Domain class ──────────────────────────────────────────
class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double initial) {
        if (initial < 0)
            throw new IllegalArgumentException(
                "Initial balance cannot be negative.");
        this.owner   = owner;
        this.balance = initial;
    }

    public void withdraw(double amount)
            throws InsufficientFundsException {
        if (amount <= 0)
            throw new IllegalArgumentException(
                "Withdrawal amount must be positive.");
        if (amount > balance)
            throw new InsufficientFundsException(amount - balance);
        balance -= amount;
    }

    public double getBalance() { return balance; }
}

// ── Usage: 3 scenarios ────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount("Alice", 100.0);

        // ✅ Scenario 1: Valid withdrawal
        try {
            acc.withdraw(40.0);
            System.out.println("Withdrew $40. Balance: $"
                + acc.getBalance());
        } catch (InsufficientFundsException e) {
            System.out.println("Error: " + e.getMessage());
        }

        // ❌ Scenario 2: Overdraft with finally block
        try {
            acc.withdraw(200.0);
        } catch (InsufficientFundsException e) {
            System.out.printf(
                "Failed: %s (shortfall $%.2f)%n",
                e.getMessage(),
                e.getShortfall());
        } finally {
            System.out.println("Transaction attempt complete.");
        }

        // ❌ Scenario 3: Bad argument
        try {
            acc.withdraw(-50);
        } catch (IllegalArgumentException e) {
            System.out.println("Validation: " + e.getMessage());
        } catch (InsufficientFundsException e) {
            System.out.println("Funds: " + e.getMessage());
        }
    }
}
▶ Output — All 3 Scenarios
$ java Main
 
// Scenario 1 — success
Withdrew $40. Balance: $60.0
 
// Scenario 2 — overdraft + finally
Failed: Insufficient funds. Short by: $140.00 (shortfall $140.00)
Transaction attempt complete.
 
// Scenario 3 — bad argument
Validation: Withdrawal amount must be positive.
🚫 Never do this: catch (Exception e) { } — swallowing exceptions hides bugs silently and makes them nearly impossible to debug. Always at minimum log the error: e.printStackTrace() or use a proper logger.
